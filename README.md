# Лабораторна: профілювання програми (FlameGraph, perf, енерговитрати, оптимізація)

Програма: множення матриць `C = A·B`, double, N=1024, 3 повтори (`matmul.c`).
Три варіанти:

| Варіант | Збірка | Суть |
|---|---|---|
| `naive_O0` | `gcc -O0` | базовий, цикли i-j-k |
| `naive_O3` | `gcc -O3` | той самий код, лише ключ компілятора |
| `opt_O3` | `gcc -O3 -DOPTIMIZED` | зміна коду: цикли i-k-j + `-O3` |

## Структура репозиторію

```
matmul.c                 вихідний код (обидві версії, перемикач -DOPTIMIZED)
Dockerfile               Debian + gcc + linux-perf + FlameGraph + GNU time
scripts/build.sh         збірка трьох бінарників
scripts/linux_all.sh     time -v, perf stat -d, perf record/report, FlameGraph, asm (arm64)
scripts/asm_x86_avx.sh   asm для x86-64: SSE2 та AVX2+FMA (docker --platform linux/amd64)
scripts/energy_mac.sh    енерговитрати через powermetrics (macOS, потрібен sudo)
results/                 усі отримані результати
```

## Як відтворити

```bash
docker build -t lab-perf .
docker run --rm --privileged -v "$PWD":/lab lab-perf ./scripts/linux_all.sh
./scripts/asm_x86_avx.sh
./scripts/energy_mac.sh
```

Flame graph (`results/flamegraphs/*.svg`) відкривати в браузері.

## Результати

Середовище: Docker Desktop (Linux 6.12 linuxkit, aarch64) на Apple M4 Pro.

| Варіант | Elapsed (`time -v`) | Прискорення |
|---|---|---|
| naive_O0 | ~20 с | 1× |
| naive_O3 | ~21–28 с (шумить) | ≈1× (не допомогло) |
| opt_O3 | ~0.30 с | ≈65–70× |

Результат (checksum) однаковий у всіх трьох: `4707274753`, тож оптимізація коректна.

### Обмеження середовища (сказати чесно на захисті)

В Docker на Mac віртуалізація не віддає апаратні лічильники PMU. Тому в `perf stat -d`
`cycles`, `instructions`, `branches`, `L1-dcache-*`, `LLC-*` мають значення `<not supported>`.
Працюють `task-clock`, `page-faults`, `context-switches`. `perf record` використовує програмний
таймер `cpu-clock` (семпли за часом), для FlameGraph цього достатньо.
Повні лічильники (IPC, cache-misses) можна зняти на реальному Linux (ноутбук, ПК, VM з
passthrough PMU), тими самими командами.

## Інтерпретація

**FlameGraph.** Вісь X це частка семплів, а не час. Ширина стовпця дорівнює частці часу
в функції, вісь Y це глибина стеку. У всіх варіантах `matmul` займає ~99.7–99.9% семплів
(`main → matmul`), `init_matrices` і `checksum` майже непомітні. Висновок: оптимізувати треба
саме `matmul`. Функції позначені `noinline`, інакше при `-O3` усе вбудовується в `main`
і граф вироджується в один стовпець.
Після оптимізації форма графа та сама (`main → matmul`), але повна «ширина» відповідає
0.3 с замість 20 с. FlameGraph показує де час, а не чому. Причину дає `perf annotate`/асемблер.

**Чому `-O3` не допоміг naive.** У i-j-k внутрішній цикл читає `B[k][j]` з кроком
N·8 = 8 КБ. Кожне читання потрапляє в новий рядок кешу, і цикл упирається в пам'ять (cache misses),
а не в обчислення. `gcc -O3` тут таки векторизує (по `j`, 2 double за раз: у `naive_O3_arm64.s:131`
`fmla v0.2d, v1.2d, v2.d[0]`, у x86 `mulpd/addpd`), але не змінює порядок обходу (`lsl x1, x0, 13`
у рядку 127 це крок 8 КБ по `B`): вектор бере 16 байт із кожного нового рядка кешу, тож
векторизація не рятує. Порядок додавання в `sum += a*b` компілятор без `-ffast-math` також не змінює:
додавання з плаваючою комою не асоціативне.

**Чому ikj допоміг.** У i-k-j внутрішній цикл іде по `j`: `B[k][j]` і `C[i][j]` читаються
послідовно (кеш-дружньо), `a = A[i][k]` винесено з циклу. Ітерації незалежні, тож компілятор
векторизує без зміни семантики: 4 `fmla` у NEON (`.2d`, 2 double в регістрі) на arm64, і
`vfmadd213pd` над `%ymm` (4 double у 256-бітному регістрі) для x86 з `-mavx2 -mfma`.

### Асемблер (п. 4.1 і 4.1.1)

- `-O0`: кожна змінна читається та пишеться в стек (`ldr/str`, `mov` у пам'ять), цикл розписаний
  дослівно, жодних векторних інструкцій.
- `-O3` naive: змінні в регістрах, цикл тугіший і навіть векторизований по `j` (`fmla v.2d` / `mulpd`),
  але доступ до `B` лишається з кроком 8 КБ, тому виграшу майже нема.
- `-O3` ikj, x86 AVX2: `vmovupd` (завантажити 4 double), `vfmadd213pd ymm` (`c = a*b + c`
  одразу для 4 double). Один рядок замінює 4 ітерації та 4 множення з додаванням.
  Це SIMD: одна інструкція, багато даних.
- `-O3` ikj, arm64 NEON: `ldp q`, `fmla v.2d` (2 double за інструкцію), розгорнуто ×2.
  На ARM немає AVX, еквівалент це NEON/SVE.
- Для порівняння SSE2 (`naive_O3_x86_sse2.s`) дає 128-бітні регістри, AVX2 256-бітні.

Файли: `results/asm/*.s`. Те саме можна показати на https://godbolt.org (`-O0`, `-O3`,
`-O3 -mavx2 -mfma`).

## Енерговитрати (п. 3)

macOS не має RAPL, тож використовуємо `sudo powermetrics --samplers cpu_power`
(CPU/GPU/ANE/Combined power у мВт, семпл кожні 200 мс). `scripts/energy_mac.sh` робить
4 заміри: `idle` (10 с спокою), `naive_O0`, `naive_O3`, `opt_O3`.

- 3.1 Система: середня Combined Power під час роботи програми.
- 3.2 Лише програма: `(P_run − P_idle) × t_run`, тобто різниця з baseline у спокої.
  Для порівняння: `E = P × t`. Оптимізований варіант працює у ~65× менше часу,
  тому споживає суттєво менше енергії, навіть якщо миттєва потужність схожа
  (чи трохи вища через SIMD-блоки).

Результати скрипт друкує в кінці (`scripts/energy_report.py`). Заміри вимагають `sudo`.

| Варіант | t, с (Mac) | Енергія за запис, Дж | Net E = E − P_idle·Δt, Дж | Середня net-потужність, Вт |
|---|---|---|---|---|
| idle (baseline) | 10 | 11.7 | 0 | P_idle ≈ 1.0 Вт |
| naive_O0 | 10.76 | 76.2 | 63.9 | 5.9 |
| naive_O3 | 3.80 | 42.4 | 37.0 | 9.7 |
| opt_O3 | 0.70 | 5.0 | 2.8 | 4.0 |

- 3.1 Система: колонка «Енергія за запис» (CPU+GPU+ANE, інтеграл потужності по семплах,
  у запис входить ~1 с спокою до і після запуску).
- 3.2 Лише програма: net E, тобто енергія мінус внесок спокою (1.0 Вт × тривалість запису).
- 4.4: `opt_O3` споживає ≈ 23× менше енергії за програму, ніж `naive_O0`, і ≈ 13× менше за `naive_O3`.
  Причина: час впав у 15× та 5.5× відповідно, а миттєва потужність не зросла: SIMD і послідовний
  доступ не змушують ядро працювати «гарячіше», а скорочують кількість тактів. Для `naive_O3`
  потужність найвища (9.7 Вт), бо ядро завантажене на 100%, але чекає на пам'ять; багато енергії
  йде на cache misses і DRAM. `E = P·t`: виграш дає в основному час.

Примітка: на Mac `clang -O3` сам прискорив naive-версію (10.8 → 3.8 с), на відміну від `gcc -O3` у Docker
(≈20 → ≈21–28 с). Різні компілятори та архітектурні деталі: clang агресивніше перебудовує цикли.
Тож на захисті порівняння -O0/-O3 для naive залежить від компілятора, а виграш ikj стабільний
в обох середовищах. Похибка замірів порядку десятих секунди, семпл 200 мс.

На Mac бінарники збираються `clang` (native arm64), тому час там інший, ніж у Docker.
